# タスクの制御

poll.sh がタスクをどう選び、どう区切り、どこで止まるか。

## 作成される PR

| 項目 | 値 |
|---|---|
| 状態 | 検証を通るまで Draft。CI とレビュアー（critic）の確認を通ったら Open にする |
| Reviewers | `REPO` の owner。Open にしたときに依頼する |
| Assignees | 付けない |
| 本文 | `prompts/pr-body.md` のテンプレートの形で、エージェントが書く |

- CI が上限まで直しても落ちたまま、critic の指摘が残ったまま、または CI を確かめられなかった（未検証）場合は、Draft のまま `agent:failed` を付け、原因を Issue に報告する。作業ディレクトリは `--retry` 用に残る
- CI が動かない変更（対象外）は、critic を通れば Open にする。critic 自体が動かなかったときも Open にし、本文にその旨が出る
- コメントで指示した修正が検証を通らなかったときは、Open だった PR も Draft に戻す
- コメントで指示した修正では、PR の本文は書き換えない

Assignees を付けないのは、**GitHub App の bot ユーザーが assignable ではない**ため。
`GET /repos/{owner}/{repo}/assignees/<app-slug>[bot]` は 404 を返す（人間のアカウントは 204）。

Reviewers の指定に失敗しても、警告を出すだけで PR は成立させる。

## フェーズ

実装のタスクは、次のフェーズを順に進む。今のフェーズはコンソールの「タスク」に出るほか、
[通知](console.md#nextcloud-talk-への通知)を登録していれば Nextcloud Talk に投稿される。
記録は `logs/<owner>__<repo>/<task-id>/phases.jsonl` に 1 行ずつ足され、最後の行が今のフェーズ。

| フェーズ | 始まる時点 |
|---|---|
| 準備 | worktree と依存の準備を始めた |
| 把握 | エージェントを起動した。Issue を読み、実装・分解・質問・回答のどれにするかを決める。実装すると決めたら、実装の方針を 1〜3 行で書いてから実装に入る |
| 実装 | エージェントが作業ツリーのファイルを書き換えたか、コミットした |
| 検証 | コミットがある状態でエージェントが終えようとし、CI の確認が始まった。critic の確認に移ると、詳細が `critic` になる |
| 公開 | エージェントが終わり、PR の本文と状態を整え始めた |

検証で差し戻されてエージェントが直し始めると、実装に戻る。

タスクは次のどれかで終わり、それも最後の行に入る。

| 終わり | ラベル |
|---|---|
| レビュー待ち | `agent:done` |
| 回答済み（コード変更なし） | `agent:done` |
| 回答待ち | `agent:awaiting-input` |
| 承認待ち | `agent:awaiting-approval` |
| 失敗 | `agent:failed` |

## ユーザーへの質問

依頼が曖昧なとき、実装前に決めるべき仕様が決まっていないとき、分解するか迷ったときは、エージェントは実装せずに質問を書く。
その中身を Issue（コメントからのタスクなら、そのコメントのスレッド）にコメントし、`agent:awaiting-input` を付けて止まる。

- `/claude` に続けて回答をコメントすると、質問した会話の続きとして作業が再開する
- 回答待ちの Issue へのコメントは、[同時進行タスクの制限](#同時進行タスクの制限)で止められない
- 実装の途中で質問した場合、それまでのコミットは push される。PR は Draft のまま

## タスク分解

大きすぎるタスクを 1 セッションで実装させると、巨大な PR・タイムアウト・予算超過のいずれかに落ちる。
そのためエージェントは、着手前に**分解すべきか**を自分で判断する。

分解する場合はコード変更を行わず、分解案を親 Issue にコメントして `agent:awaiting-approval` で止まる。
sub issue はこの時点では作らない。作ってしまうと `agent:queued` が付いた sub issue が
次の poll で実装され始め、案を確認する前に走り出してしまう。

```
16:42:10 [issue-7-...] 分解案を提案します (3 件)
16:42:18 [issue-7-...] 承認待ち: `/claude approve` のコメントで sub issue を作成します
```

案への応答は 3 通り。

| 応答 | 動作 |
|---|---|
| `/claude approve` とコメント | 最新の案のとおり sub issue を作成し `agent:done` に進む。エージェントは起動しない |
| `/claude` に続けて修正点を書く | 前回の案を渡した上でエージェントが案を作り直す（または「分解せず実装して」ならそのまま実装する） |
| ラベルを外す / Issue を閉じる | 却下。案のコメントは残るが何も起きない |

承認をうかがうコメントには `reason` と各 sub issue の `title` / `outline` だけを載せ、
`body` は畳んだ `plan.json` に入れておく。承認時に使われるのはその `plan.json` なので、
承認前にコメントを編集してタイトルや本文を直しても構わない。承認済みの案はマーカーが
書き換えられ、もう一度 `/claude approve` しても重複して作られない。

判断基準は `prompts/decompose.md` にある。要点は次のとおり。

- **1 つの PR は 1 つの関心事に絞る**。独立してレビュー・revert できる関心事が 2 つ以上あるなら分ける
- **レイヤ（DB / API / Web）をまたぐ変更はレイヤごとに分ける**。DB → API → Web の順に先行させる
- **機能改修とリファクタリングを混ぜない**。リファクタが前提なら先行する別 sub issue に切り出す
- 整形・リネーム・依存更新のような機械的な差分は、意味のある変更と混ぜない
- 本体と不可分なテスト・ドキュメントは切り出さない。単体でレビューできなくなる
- 分解するか迷ったときは、実装も分解もせず、[ユーザーに質問する](#ユーザーへの質問)
- 過去の PR の粒度は根拠にしない。分解しない場合もその理由を最終メッセージに 1 行残す

### 仕組み

エージェントの `gh` トークンは読み取り専用なので、**自分では sub issue を作れない**。
分解結果は worktree 直下の `.mopu-agent-plan.json` に書かせる。
それを `lib/plan.sh` が読んで案のコメントを投稿し、承認されたら sub issue を作る。

```json
{
  "reason": "この分け方にする理由",
  "sub_issues": [
    { "title": "サブタスク", "outline": "1 行の要約", "body": "## 目的\n...\n## 完了条件\n- [ ] ..." }
  ]
}
```

- 承認で作成される sub issue には `agent:queued` が自動で付く。次回の poll から実装が走る
- 件数は `MAX_SUB_ISSUES`（既定 5）で頭打ちにする
- sub issue は REST の sub-issues API で親に紐付く（`sub_issue_id` は Issue の `number` ではなく `id`）
- sub issue の PR は `Closes #<sub issue>` で sub issue しか閉じないので、親は `poll.sh` が毎回の
  先頭で閉じる。`agent:done` の open な Issue のうち sub issue を 1 件以上持ち、そのすべてが
  closed（理由は問わない）なら、コメントを付けて completed で閉じる。人間が後から足した
  sub issue も数えるので、それが開いている間は親も開いたまま
- 生成した sub issue の本文には `<!-- mopu-agent:sub-of #N -->` が入る。
  **このマーカーか REST の `parent_issue_url` を持つ Issue は再分解されない**（無限分解のガード）。
  後者があるので、手動で親に紐付けた Issue も対象になる

## 1 セッションで PR の全コメントに対応する

同じ作業対象への `/claude` コメントは、1 回の poll で 1 つのタスクに畳んでから
エージェントへ渡す。PR の会話コメント・レビューコメント・元 Issue へのコメントは
どれも同じブランチを触るので、別々のセッションで順に処理しても後のセッションが
前の変更を読み直すだけになり、指示どうしの矛盾も見つけられない。

返信は畳む前のスレッドへ個別に返す。エージェントは指摘ごとの返信を
`.mopu-agent-replies.json`（作業ディレクトリの外）に書き、run-task.sh がそれを配る。

```json
{
  "replies": {
    "<コメントID>": "そのコメントへの返信"
  }
}
```

- 書かれなかった ID には、最終メッセージの全文が代わりに入る
- PR のリンクとコミット一覧は繰り返しても意味がないので、最後のコメントにだけ付ける
- 失敗の報告も最後のコメントにだけ返る

タスクの行は fd 3 で読む。`claude` は TTY でない標準入力を読み切るため、fd 0 のまま
ループを回すと最初に起動した `claude`（利用枠の確認を含む）が残りのタスクを食う。
コメント由来のタスクはそこで消え、`last-poll` が進んだあとは二度と検出されない。

## 対象リポジトリの指示

対象リポジトリの次のファイルを、ベースブランチの版から読んでエージェントに渡す。

- ルートの `CLAUDE.md` と `.claude/CLAUDE.md`。どちらも無ければ `AGENTS.md`
- `CLAUDE.md` の中の `@path` が指すファイル（4 段まで）
- `.claude/rules/` の `.md`
- サブディレクトリの `CLAUDE.md`

渡した内容はタスクごとに `logs/<owner>__<repo>/<task-id>/project-memory.md` に残る。

- PR の中でこれらのファイルを書き換えても、その PR のタスクには効かない。マージしてベースブランチに入ってから効く
- `.claude/settings.json` の hooks や permissions、skills、MCP の設定は読まない
- `@path` は、リポジトリの中を指す相対パスだけを展開する。絶対パスや `~` で始まるパスは展開しない
- `paths` で範囲を絞った rule とサブディレクトリの `CLAUDE.md` も、範囲を見出しに書いたうえで最初から渡す。範囲外のファイルを扱うときに従わないかどうかは、エージェントの判断に任される
- 合計が 60,000 文字を超えた分は渡さず、省いたファイル名だけを伝える
- 実行環境についての指示（`docker compose` で確かめる、など）は sandbox の中ではできない。エージェントには、mopu-agent の制約を優先して `run-container` や CI に置き換えるよう伝えている

## 差し戻しからの学習

コンソールの設定で、リポジトリの「差し戻しから基準を学ぶ」をオンにすると使える。既定はオフ。

エージェントの PR がマージされ、その PR に差し戻し（PR ができてからマージまでに、コメントで依頼した実行）があった場合、その差し戻しから次に守る基準の案を作らせ、対象リポジトリに Issue として出す。案を採るなら、人間が文書に置く。置いてベースブランチに入った基準が、以降のタスクに[対象リポジトリの指示](#対象リポジトリの指示)として届く。

- Issue の本文の頭には、置き場所の案（作業の仕方は `.claude/rules/`、製品の仕様の判断は `docs/` とそれを指す rule）、置く文面の案、その理由が載る。元の差し戻しコメントなどの根拠は、その下に折りたたまれて載る
- 差し戻し後の構造のほうが、使うときと改修するときに考えることが減っていなければ、その場面に限った差し戻しとして案にしない。案にしなかった差し戻しと理由は、ポーリングのログに出るほか、同じ回に出た最後の Issue の末尾に折りたたまれて載る
- エージェントは基準を自分では置かない。`.claude/` は Claude Code の保護パスで、エージェントの権限では書き込みが拒否されるため
- Issue にはラベルを付けない。mopu-agent のタスクにはならない
- 学習が出した Issue を not planned で閉じると、以降の学習で同じ趣旨の案は出ない。開いている Issue と同じ趣旨の案も出ない
- 1 つの差し戻しから出る Issue は 3 件まで。案にするものが無ければ Issue は出ない
- 学習は通常のタスクの後ろに回り、1 回のポーリングで 1 件だけ処理する。利用枠のゲートと、1 回のポーリングで処理する上限は通常のタスクと同じく効く
- オンにすると、過去にマージされた PR も古い順に対象になる。対象は `state/spend.jsonl` に実行の記録が残っている PR に限る
- 失敗した PR は、次のポーリングでもう 1 回だけやり直す

対象リポジトリの指示が 30,000 文字を超えると、棚卸しが走る。`.claude/rules/` の重複をまとめ、矛盾を揃え、現在のコードに当てはまらなくなった rule を消す案が、Issue として出る。指示の中身が変わるまで、棚卸しは出し直さない。

## 会話の引き継ぎ

`--retry` と PR コメントへの対応は「前回の続き」なので、`claude` のセッションを
`--resume` で再開する。前回どのファイルを読み、何を却下したかが会話に残っているため、
同じ調査をやり直さずに済む。

| タスク | 会話 |
|---|---|
| ラベル由来の Issue | 毎回新しく始める |
| コメント由来（PR のレビューを含む） | 前回の会話を再開する |
| `--retry` | 前回の会話を再開する |

会話 ID は Issue 番号ごとに `state/repos/<owner>__<repo>/sessions.json` へ控える。作業ツリーと違って成功時にも
消さない。レビューが数日後に来ても、その PR を書いたときの判断から続けられる。

`--fork-session` を付けて会話を分岐させるので、元の会話はそのまま残る。失敗しても
同じ地点から何度でもやり直せる。

次の場合は引き継がない。

- **打ち切りで終わった前回**。`timeout` の 124 と、`--max-budget-usd` による
  `error_max_budget_usd` がこれにあたる。膨らんだ context のまま再開しても
  同じ壁にぶつかるので、控えていた会話 ID を捨てて次回は新しく始める
- **保持期間を過ぎた会話**。`--resume` は課金ゼロで即座に落ちる（stderr に
  `No conversation found with session ID`）。それを見てから会話なしで実行し直す

### コストへの影響

再開は context を節約しない。**増やす。**

`logs/` の実績 19 件で測ると、新しく始めたタスクが初回リクエストで送る context は
20,625〜30,938 トークン。会話を再開すると、これが前回の終了時点の context
（24,559〜47,640 トークン）に置き換わる。同じタスクで比べた積み増しは
0〜17,210 トークン、平均 4,559 トークン。

プロンプトキャッシュの TTL は最長 1 時間で、レビュー待ちで時間が空いた PR コメントでは
効かない。それでも引き継ぐのは、再探索の削減と判断の一貫性のほうが効くため。

## 同時進行タスクの制限

poll.sh は 1 回の実行で最大 `MAX_TASKS_PER_RUN` 件（既定 3）を逐次処理する。
放っておくと PR が何本も並び、レビューされないまま溜まる。

リポジトリが複数あるときも、この上限は**全リポジトリの合計**で数える。
リポジトリは 1 つずつ順に処理し、先頭にするリポジトリを実行ごとに 1 つずつずらす。
あるリポジトリで利用枠やレート上限に当たったら、残りのリポジトリもその回は処理しない。
clone の失敗や App の未インストールなど、1 つのリポジトリだけの失敗では他のリポジトリは止まらない。

`MAX_OPEN_AGENT_PRS`（既定 1、リポジトリごと）は、**そのリポジトリに未マージの `agent/issue-*` PR がある間、新しい Issue への着手を止める**。

```
16:40:02 進行中の PR: 1 件 (agent/issue-4)
16:40:02 進行中の PR が 1 件あるためスキップします: #7（マージ/クローズ後に再検出されます）
```

- スキップされたタスクは `agent:queued` のまま残る。PR がマージ/クローズされた後の poll で再検出される
- **進行中 PR とその元 Issue への `/claude` コメントは例外**として常に処理される。
  塞ぐとレビュー指摘を反映できず、「PR が open なので着手できない / 着手できないので PR が進まない」で詰まる。
  PR へのコメントは、ブランチ名 `agent/issue-<番号>` から元 Issue の番号に読み替える。
  読み替えるのは作業対象の番号だけで、報告はコメントが来た PR 側に返る
- `agent:awaiting-input` と `agent:awaiting-approval` の Issue への `/claude` コメントも例外として処理される
- `--task` での手動指定もゲートを通さない
- `0` にすると無制限になる

## 利用枠のゲート

`claude -p "/usage"` で 5 時間枠と週次枠の使用率を取得する。閾値を超えていればタスクを開始しない。
`/usage` はローカルコマンドとして処理されるので、**API 呼び出しを伴わず枠を消費しない**（約 1.8 秒）。

```
16:30:23 利用枠: 5h=81% (閾値 50%) / 7d=34% (閾値 80%)
16:30:23 5時間枠が 81% に達しています。resets Aug 23, 8:20pm (Asia/Tokyo) 以降に再実行してください
```

- タスク 1 件ごとに測り直すので、連続処理で閾値を跨がない
- `/usage` の出力を解釈できなければ**安全側に倒して起動しない**
- 実行中に `rate_limit_event` が `allowed_warning` / `rejected` になったら、以降のタスクを打ち切る
- 実績は `state/spend.jsonl` に記録される（コスト（会話を再開したタスクでは、再開してから増えた分）、実行前後の 5h 使用率、Issue 番号、タスクの種類と結果、拒否されたコマンドの数、実行した mopu-agent のコミット）
