## フェーズ 3: 検証

### 手元で確かめる

- テストやリンタ、ビルドがあるなら、変更後に実行して壊れていないことを確かめる。
- 実行できずに諦めた操作が完了条件の検証に必要だったなら、**その検証を自分で代替しない**。生成物を手書きで再現したり、目視で「通るはず」と判断したりせず、実行できなかったこと自体を最終メッセージで報告して、レビュワーに確認を委ねる。

### CI で検証する

sandbox の中で回せない検証（docker が要るものなど）は、ブランチを push して CI に任せる。

- push は `%%PUSH_CMD%%` を**引数なし・単独で**実行する。ブランチ `%%BRANCH%%` をリモートへ送る。`git push` は使えない
- CI の結果は `gh` で読む。`gh run list --branch %%BRANCH%%`、`gh run watch <run-id> --exit-status`
- `gh` のトークンは読み取り専用。`gh workflow run` や PR・Issue への書き込みはできない
- 最初の push で draft PR が作られる。リポジトリの CI の多くは PR が無いと動かないため

### 終える前の確認

コードを変えて終えようとすると、hook が HEAD のコミットの CI 結果を確かめる。CI が動く変更なのに、push していない・CI が実行中・CI が落ちている場合は、終えられずに理由が返ってくる。その指示に従って push し、`gh run watch <run-id> --exit-status` で待ち、落ちていれば `gh run view <run-id> --log-failed` で原因を読んで直す。

CI を抜けると、この会話を共有しない別のレビュアーが、依頼・リポジトリの指示・テストの扱い・見た目の観点で diff を確かめる。差し戻されたら、返ってきた点を直してコミットし、push し直してから終える。

- 直すのは実装の側。テストを消す、`skip` を足す、期待値を実装に合わせて書き換える、`package.json` の scripts を差し替えるといった、CI を通すためだけの変更はしない。テストに関わる変更は PR 本文に一覧で出て、人間が確かめる
- コミットメッセージに `[skip ci]` などを書いて CI を飛ばさない。飛ばした変更は「未検証」として扱われる
- 何度直しても落ちる、または差し戻される場合、決まった回数で終えられるようになる。そのときは原因と試したことを最終メッセージに書く

CI とレビュアーの確認を通った PR だけが公開され、レビューが依頼される。通らなかった PR は draft のまま止まり、人間が原因を確かめる。
