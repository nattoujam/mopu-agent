## タスクが大きすぎる場合

**実装に着手する前に、必ずこの判定を先に行うこと。** 判定を飛ばして実装を始めてはいけない。

### 分解する

次のいずれか 1 つでも当てはまるなら、**実装せずに分解する**。判断に例外は設けない。

- **1 つの PR は 1 つの関心事に絞る。** 独立して説明・レビュー・revert できる関心事が 2 つ以上あるなら分ける
- **Issue 本文が複数の成果物を列挙している。** 箇条書きや番号付きで「あれもこれも」と並んでいて、各項目が独立してレビューできるなら、まとめて実装しない
- **機能改修とリファクタリングを同じ PR に混ぜない。** 前提としてリファクタが必要なら、それを先行する別のサブタスクに切り出し、依存順序を本文に書く
- 整形・リネーム・依存の更新のような機械的な差分は、意味のある変更と混ぜるとレビューを潰すので必ず分ける
- 複数のレイヤ・コンポーネントにまたがり、実装に順序依存がある
- 実装前に決めるべき仕様の未確定点がある

行数の目安として、**1 つの PR の差分が 400 行を超える見込みなら分解を疑う**。
一度にレビューして欠陥を見つけられるのは 200〜400 行程度までで、それを超えると
発見率が落ちることが知られている（SmartBear が Cisco で 2,500 件のレビュー・
320 万行を分析した結果）。Google の eng-practices も「100 行が妥当、1000 行は
大きすぎ」としている。

ただし**ファイル数に固定の閾値は置かない**。1 ファイルの 200 行は問題なくても
50 ファイルに散っていれば大きすぎる、というように、数え方では決まらない。
最終的な判断は行数ではなく**関心事の数**で行うこと。
「1 つずつなら簡単だから、まとめてやっても簡単」という理由で分解を見送らない。
レビューする側の負荷は、変更の難しさではなく関心事の数で決まる。

### 分解しない

- 単一の関心事で完結する、または既に十分小さい
- 質問への回答だけで済み、コード変更が要らない
- 本体の変更と不可分なテスト・ドキュメントの更新（切り出すと単体でレビューできないので、同じ PR に入れる）

上の「分解する」のどれにも当てはまらないなら、そのまま実装する。
意味なく細かく割るのも害なので、1 つの関心事を工程ごとに刻むような分解はしない。

### 分解する場合の手順

1. コードの変更と `git commit` を**一切行わない**
2. 作業ディレクトリの直下（`repo/` の中ではない）に `.gh-agent-plan.json` を Write ツールで作成する
3. 最終メッセージには、なぜ 1 セッションで完結させないのかを人間向けに書く

`.gh-agent-plan.json` の形式:

```json
{
  "summary": "分解の要約を 1〜2 文で",
  "reason": "1 セッションで完結させない理由",
  "sub_issues": [
    {
      "title": "サブタスクのタイトル",
      "body": "## 目的\n何を達成するか\n\n## 対象\n変更が想定されるファイル\n\n## 完了条件\n- [ ] 検証可能な条件\n\n## 依存\n先に完了しているべきサブタスクがあれば書く（まだ番号は振られていないのでタイトルで指す）"
    }
  ]
}
```

- `sub_issues` は 1 件以上、**最大 %%MAX_SUB_ISSUES%% 件**
- 各サブタスクは、それ単体で 1 つの PR になる粒度にする
- `body` は、この Issue を読んでいない人が着手できるだけの情報を含める
