### 分解するかの判定

把握のフェーズで、実装すると決める前にこの判定を行う。

#### 分解する

次のいずれかに当てはまるなら、実装せずに分解する。ただし、下の「分解しない」に当たる場合と、分解するか迷った場合は除く。

- **1 つの PR は 1 つの関心事に絞る。** 独立して説明・レビュー・revert できる関心事が 2 つ以上あるなら分ける
- **Issue 本文が複数の成果物を列挙している。** 箇条書きや番号付きで「あれもこれも」と並んでいて、各項目が独立してレビューできるなら、まとめて実装しない
- **レイヤをまたぐ変更は、レイヤごとに PR を分ける。** レイヤは DB（スキーマ・マイグレーション）、API（クエリ・ルート）、Web（UI）の 3 つ。DB → API → Web の順に先行させ、後続の本文に依存を書く。レイヤごとに検証の仕方（マイグレーションの適用、API の疎通、Storybook / VRT）と戻しやすさが違うので、まとめると一番慎重に見たい DB の差分が UI の差分に埋もれる
- **機能改修とリファクタリングを同じ PR に混ぜない。** 前提としてリファクタが必要なら、それを先行する別のサブタスクに切り出し、依存順序を本文に書く
- 整形・リネーム・依存の更新のような機械的な差分は、意味のある変更と混ぜるとレビューを潰すので分ける

行数の目安として、**1 つの PR の差分が 400 行を超える見込みなら、関心事が 2 つ以上混ざっていないかを確かめる**。
一度にレビューして欠陥を見つけられるのは 200〜400 行程度までで、それを超えると
発見率が落ちることが知られている（SmartBear が Cisco で 2,500 件のレビュー・
320 万行を分析した結果）。Google の eng-practices も「100 行が妥当、1000 行は
大きすぎ」としている。

ただし**ファイル数に固定の閾値は置かない**。1 ファイルの 200 行は問題なくても
50 ファイルに散っていれば大きすぎる、というように、数え方では決まらない。
最終的な判断は行数ではなく**関心事の数**で行うこと。
「1 つずつなら簡単だから、まとめてやっても簡単」という理由で分解を見送らない。
レビューする側の負荷は、変更の難しさではなく関心事の数で決まる。

#### 分解しない

- 単一の関心事で完結する
- 質問への回答だけで済み、コード変更が要らない
- 本体の変更と不可分なテスト・ドキュメントの更新（切り出すと単体でレビューできないので、同じ PR に入れる）
- レイヤをまたいでいても、片側が数行で単体では説明のしようがない（既存のレスポンスに 1 フィールド足して表示するだけ、など）

上の「分解する」のどれにも当てはまらないなら、そのまま実装する。
意味なく細かく割るのも害なので、1 つの関心事を工程ごとに刻むような分解はしない。

分解するかどうか迷ったら、実装も分解もせず、上の「ユーザーに聞く」の手順で迷っている点を聞く。

**過去の PR やコミットの粒度を根拠にしない。** 前例は当時の基準で切られたものなので、
判定は毎回この文書の基準だけで行う。

分解しない場合も、PR 本文のテンプレートの「分解しない理由」に 1 行書く。
判定を飛ばしたのか、判定して見送ったのかを外から区別できるようにするため。

#### 分解する場合の手順

1. コードの変更と `git commit` は行わない
2. `%%PLAN_FILE%%` を Write ツールで作成する。このパスをそのまま使う。このファイルは git から無視される設定になっているので、コミットはしない

案はそのまま実行されず、まず Issue にコメントして人間の承認を待つ。承認をうかがう
コメントの本文に並ぶのは `reason` と各サブタスクの `title` / `outline` で、`body` は
折りたたみの中に載り、承認後に sub issue の本文になる。最終メッセージは投稿されない
ので、判断の説明は `reason` に書く。

`%%PLAN_FILE%%` の形式:

```json
{
  "reason": "この分け方にする理由を 1〜2 文で",
  "sub_issues": [
    {
      "title": "サブタスクのタイトル",
      "outline": "何を変えるかを 1 行で（承認をうかがうコメントに並ぶ）",
      "body": "## 目的\n何を達成するか\n\n## 対象\n変更が想定されるファイル\n\n## 完了条件\n- [ ] 検証可能な条件\n\n## 依存\n先に完了しているべきサブタスクがあれば書く（まだ番号は振られていないのでタイトルで指す）"
    }
  ]
}
```

- `sub_issues` は 1 件以上、**最大 %%MAX_SUB_ISSUES%% 件**
- `outline` は「レビュアーがコメントだけ読んで分け方の良し悪しを判断できる」粒度にする。対象ファイルや実装手順は `body` に書く
- 各サブタスクは、それ単体で 1 つの PR になる粒度にする
- `body` は、この Issue を読んでいない人が着手できるだけの情報を含める
