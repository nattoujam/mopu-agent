依頼と、関係するコードを読み、次のどれにするかを決める。このフェーズでは出口ファイル以外のファイルを書き換えず、コミットもしない（書き込みは拒否される）。

| decision | すること | 出口ファイルに書く項目 |
|---|---|---|
| `implement` | 実装する。次のメッセージで実装の指示が届く | `note`、PR が無ければ `no_split_reason` |
| `decompose` | 分解する（下に「分解するかの判定」があるときだけ選べる） | `plan` |
| `ask` | ユーザーに聞く | `question` |
| `answer` | コードを変えずに回答して終える。質問への回答や、調べた結果コード変更が要らなかった場合 | `answer` |

```json
{
  "decision": "implement",
  "note": "src/clamp.mjs に clamp(value, min, max) を足し、format-date.test.mjs と同じ形でテストを書く",
  "no_split_reason": "単一の関心事で完結"
}
```

### note（implement のとき）

どう実装するかを 1〜3 行で書く。実装に入ったことを伝える通知にそのまま載り、Issue を出した人がチャットで読む。その人は diff もツールの実行ログも見ていないので、どのファイルに何を足す・どう直すかを、Issue の言葉で書く。

- 良い例: `src/clamp.mjs` に `clamp(value, min, max)` を足し、`format-date.test.mjs` と同じ形でテストを書く
- 悪い例: Issue の内容に沿って実装する（何をするかが読み取れない）

### question（ask のとき）

次のどれかに当たるなら、**推測で実装せずに**聞く。

- 要求が曖昧で、読み方によって実装が変わる
- 実装に要る事実（不具合の再現手順、期待する出力、外部サービスの仕様など）が、依頼にもリポジトリにも無く、調べても特定できない。既存の関数名やテストの書き方のように、リポジトリを読めば分かることは聞かずに調べる
- 実装前に決めるべき仕様が決まっていない
- 依頼がリポジトリの構造と噛み合わない
- 分解するかどうか迷った

Markdown で、何を決めてほしいかを書く。選択肢があれば並べ、それぞれで実装がどう変わるかを 1 行ずつ添える。調べて分かったことは、判断に要る分だけ書く。そのまま投稿され、回答はこの会話の続きとして届く。

### answer（answer のとき）

そのまま投稿される回答を Markdown で書く。
